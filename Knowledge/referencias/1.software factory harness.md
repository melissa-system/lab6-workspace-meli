# Build an AI software factory on the rsc harness

## Context

You are working in a shared AI workspace: a git repository that holds the
durable knowledge, tooling and process for one software product whose code
lives in one or more separate repositories. The workspace may be completely
empty, or it may already contain notes, docs, requirements, backups or a
previous layout.

You do not know the product, the repositories, the git host, the people or
the conventions in advance. **Discover what you can from the workspace;
ask the person for the rest.** Never invent a repository URL, a trunk
branch, a stack, a verify command or a non-negotiable rule.

Conventions you must keep (or introduce if absent):

- Progressive disclosure: every folder that matters has an `AGENTS.md`
  (or `README.md`) whose first line under the title is `> **TL;DR:** …`.
- Code clones live git-ignored under `Repos/<PRODUCT>/<repo>/`.
- Per-repo tooling (OpenSpec, Graphify, test harnesses) runs from inside the
  repo that owns it, never from the workspace root.
- Tests and local runs never touch a shared or production database.

Work on a new branch `harness/rsc-factory` cut from the workspace's default
branch (detect it; if the workspace has no git history, initialise it and
ask whether a remote should be added). You may restructure or drop anything
in the workspace; keep the value, not the files.

## Step 0 — discover, then ask once

1. Inspect the workspace: git remotes, default branch, existing folders,
   any `AGENTS.md`/`README.md`, any file that looks like knowledge, domain
   stories, requirements, DB backups, credentials or `.env`.
2. If `Repos/` or clones exist, read each clone's root files to infer
   stack, package manager, test command, trunk and whether it has
   `openspec/` or `graphify-out/`.
3. Ask the person, **in one batched message**, only what you could not
   infer. Typical items:

   | Need | Ask |
   |---|---|
   | Product name | short id used for `Repos/<PRODUCT>/` and `02-DOCS/wiki/systems/<product>/` |
   | Repositories | for each: id, clone URL, trunk branch, stack, verify commands, kind (frontend / backend / worker / service), OpenSpec root if any, whether it is graphified |
   | Git host and CLI | which host (and its CLI, if any) the factory should use for PRs/MRs and CI |
   | Error tracker | which one, if any, feeds the `sentry`-style intake source |
   | Users' language | the language end-user-facing text must be reviewed in |
   | Non-negotiables | project rules that must enter the constitution (architecture constraints, forbidden APIs, data rules, release rules) |
   | Existing knowledge | where old notes/requirements/backups are, and what may be deleted |
   | Secrets | whether anything already in the workspace contains credentials and must be removed and rotated |
   | Models | confirm the model slugs available in this environment for each role (see pipeline), or accept the defaults with fallbacks |

   Record the answers in `02-DOCS/wiki/systems/<product>/overview.md` and
   `factory/factory.config.json`; they become the single source of truth.

## Step 1 — install the meta-harness

Read https://github.com/ericrisco/rsc-harness first. Install it for real:
`npx @ericrisco/rsc@latest onboard` with targets Cursor + Claude Code,
workflow `branches` (trunk closed to the agent), software scope `complex`;
accept the plan. Then migrate the existing knowledge into its layout:

- system/architecture notes → `02-DOCS/wiki/systems/<product>/`
- domain stories / user stories → `02-DOCS/wiki/<domain>/`
- requirements, backups, raw sources → `02-DOCS/raw/`
- anything with a secret in it: delete it, note the leak in `decisions.md`,
  list it in the final report as "rotate".

Write `02-DOCS/wiki/index.md` (the map), `log.md`, `gaps.md`, and ratify
`02-DOCS/wiki/sdd/constitution.md` (status ≠ draft) with, at minimum:
branches + PR, TDD per task, evidence not claims (quote test-run artefact
paths, never "tests pass"), never the shared/production DB, OpenSpec per
repo, Graphify-first in any graphified repo, no AI co-author trailers,
specs are the contract — plus every project non-negotiable the person gave
you in Step 0. Add one `01-TOOLS/<tool>/` folder per external system the
person named (git host, error tracker, …) from rsc's `_TEMPLATE` (README,
CREDENTIALS, `.env.example`, `test_connection`; `.env` git-ignored).

## Step 2 — build the factory on top (`factory/`)

Goal: any request → spec → TDD build → four independent reviews → approval →
decide whether a human must approve → land. Persistent memory, full trace,
errors correctable. Three foundations:

1. A defined process: every stage has inputs/outputs, is repeatable and
   auditable.
2. Code for deterministic work, agents for reasoning, humans at approval
   points.
3. A shared brain (`02-DOCS/wiki/`) every agent consults before acting:
   constitution → system overview → decisions → domain page.

### Pipeline and models

```
Entry ─► Spec Writer ─► Builder (TDD, worktree) ─► 4 Reviewers ─► Approver ─► Human? ─┬─► MAIN ─► Production
 (tracker, issue,     Opus              Opus         Sol·Sol·Astra·Sonnet    Opus    Opus/Sol  └─► PR (person) ─► Production
  chat, inbox)                                         ▲                       │
                                                       └── changes-requested ──┘
```

Model names above are defaults. Verify each slug is available in this
environment; if not, ask the person or configure the fallback declared in
`factory.config.json`. The Security reviewer's model family must differ
from the Builder's.

- **Entry**: `factory intake --source chat|issue|tracker|inbox` normalizes
  the request into `02-DOCS/wiki/sdd/runs/<run>/intake.md`. Run id
  `f-YYYYMMDD-xxxx`; branch `factory/<run>-<slug>`; worktree
  `<repo>/.worktrees/<run>/`. Several runs may be open at once; each is
  isolated by id, branch, worktree, trace.
- **Spec Writer (Opus)**: consults the brain, writes
  `02-DOCS/wiki/sdd/specs/<run>.md` with sections Intent, Scope, Out of
  scope, Brain consulted (must link wiki pages), Acceptance criteria, Tasks
  (each with a `done-check:`), Risk (`impact_estimate: low|high`), Target.
  Mirrors it into the repo's OpenSpec change when the repo has one.
  `factory spec-check` validates structure; `spec-approve` by the agent only
  for low-impact non-backend specs, otherwise `spec-approve-human --by`
  (human-only).
- **Builder (Opus)**: `factory worktree` creates the worktree from
  `origin/<trunk>`; strict TDD per task (test first, observed failing, then
  implementation), one commit per task, the repo's verify commands from
  `factory.config.json`, then `factory review-open` freezes the head and
  writes a review package.
- **Four reviewers, fresh context, dispatched in parallel as separate
  subagents** on the same head, each writing
  `runs/<run>/reviews/round-N/<role>.md` with frontmatter `verdict`, `sha`,
  `model`:
  - Security — Sol (must differ from the Builder's model family)
  - UX — Sol (steps, error states, wording in the users' language from
    Step 0, alignment with the domain wiki)
  - UI — Astra (visual; `NOT_APPLICABLE` when no UI changed; configure a
    vision-capable fallback if Astra is not an available model slug)
  - Code — Sonnet (brain, architecture, conventions, tests as evidence)
- **Approver (Opus)**: `factory approve --verdict approved|changes-requested`.
  Refuses while a report is missing, stale (sha ≠ head), on the wrong model,
  or any reviewer says CHANGES_REQUESTED; refuses without a `subagent.start`
  trace per reviewer role after the round opened (that is the evidence of
  fresh context). `changes-requested` loops back to the Builder.
- **Human? (Opus or Sol)**: `factory classify --impact --human-required
  --reasons`. Code computes a floor from changed paths and repo kind
  (backend repos, migrations/SQL, app configuration, entry points, auth,
  Dockerfile, CI, dependency manifests, hooks, `factory/**` → high; extend
  the list with what the person's stack needs). Final =
  stricter(agent, floor): the agent may raise impact, never lower it.
  `low` → MAIN path (merge-local by the agent); `high` → PR a person merges.
- **Release**: `factory release` prints the exact landing commands for the
  configured git host; `factory done --merged <sha>|--pr <url>` closes the
  run and appends to `decisions.md`.

### Controls (enforce in code, not prose)

Write hooks under `factory/hooks/` wired into `.cursor/hooks.json`
(beforeShellExecution fail-closed, preToolUse on Write/Edit/Delete,
subagentStart/Stop, afterShellExecution) and `.claude/settings.json`
(PreToolUse on Bash|Write|Edit|MultiEdit|Task). All share one pure
`judge(command)` that:

- denies commit/merge/push on the trunk of any known repo by the agent
  (trunk names come from `factory.config.json`, not a hard-coded list);
- denies commits on a factory branch before spec approval;
- allows landing (local merge, push to trunk, host-CLI merge) only with
  `approval.json` + `release.json` for the exact head sha, and for
  `human_required: true` only after `factory human-approve --by` (human-only);
- denies the human-only commands to the agent (`human-approve`,
  `spec-approve-human`, `unlock-trunk`) in every spelling (`factory …`,
  `node factory/bin/factory.mjs …`, `npm run factory -- …`);
- asks the person for destructive commands (rm -rf, reset --hard, force
  push, branch -D, drop table, worktree remove --force);
- tracks `git switch/checkout` inside a `&&` chain so `git switch <trunk> &&
  git commit` is denied; follows `cd` and `git -C`;
- ignores quoted text (`grep "git commit"` is not a commit);
- fails open when the directory is not a known repo.

Protect the ledgers: deny agent edits to `run.json`, `approval.json`,
`release.json`, `trace.jsonl`; ask before edits to `factory.config.json`,
the hooks files and gate/guard libs (override `FACTORY_ADMIN=1` for people).
Every hook decision and every stage change appends a line to
`runs/<run>/trace.jsonl`.

`README.md`, `.cursor/rules/0*.mdc` for per-repo tooling (OpenSpec,
Graphify, any repo-specific verification harness), and `Repos/**/AGENTS.md`
with the clone commands for every repo the person named. Node ≥ 18, ESM,
no dependencies.

## Constraints

- rsc's own hooks and skills stay intact; `rsc sync` must not break the
  factory and `factory sync` must repair the hook wiring after it.
- Deterministic code decides; agents reason; people approve. Never make an
  agent able to grant its own human approval.
- Every refusal message says the way out.
- No AI co-author trailers in commits. Keep tests outside the real wiki
  (temp dirs).
- Nothing project-specific is hard-coded in `factory/lib/**` or
  `factory/hooks/**`; it all comes from `factory.config.json`.
- Ask before deleting any pre-existing content you cannot classify as
  knowledge, raw source, or secret.
- Finish with: `node --test "factory/tests/*.test.mjs"` green,
  `factory sync --check` clean, `factory doctor` healthy, one commit on
  `harness/rsc-factory`, and a report listing anything a person must do
  (rotate leaked keys, unavailable models, missing CLIs/clones, questions
  left unanswered).
